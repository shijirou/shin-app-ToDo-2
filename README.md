## 起動方法
自分のパソコン（Windows）で動かす手順です。

### 必要なもの
| ソフトウェア | 使うところ |
|---|---|
| Docker Desktop | DB（PostgreSQL）を動かす |
| Java 25（Eclipse Temurin など） | API（Spring Boot）を動かす |
| Node.js 24（npm 付き） | 画面（React + Vite）を動かす |

※ 詳しい版は[使用バージョン](#使用バージョン)を見てください。

### はじめて動かすとき（1回だけ）
```powershell
cd frontend
npm install   # 画面で使う部品（React・dnd-kit など）を入れる
```

### 起動する（毎回）
次の順番で起動します。ターミナル（PowerShell）は、API 用と画面用で2つ使います。

| 順番 | 起動するもの | 場所 | コマンド | ポート |
|---|---|---|---|---|
| 1 | Docker Desktop | — | アプリを開く | — |
| 2 | DB（PostgreSQL） | リポジトリ直下 | `docker compose up -d` | 5432 |
| 3 | API（Spring Boot） | `backend` | `.\gradlew.bat bootRun` | 8080 |
| 4 | 画面（Vite） | `frontend` | `npm run dev` | 5173 |

ブラウザで **http://localhost:5173** を開くと、ボードが表示されます。

- 画面の `/api` へのアクセスは、Vite のプロキシが API（8080）へ取り次ぎます。
- はじめて起動したときは、テストデータ（ToDo・進行中・完了の3つのリスト）が入ります。
- ポートは必ず上の表の番号を使います。「使用中」で起動できないときは、[CLAUDE.md](CLAUDE.md) の「サーバーのポートのルール」の手順で、前に起動したものを止めてから起動し直します。

### 止める
- 画面・API: それぞれのターミナルで `Ctrl + C`
- DB: リポジトリ直下で `docker compose down`（データは消えません）

### 自動テストを動かす
プログラムを直したあとに動かすと、ほかの機能を壊していないかを数秒で確かめられます。

| 対象 | 場所 | コマンド | 内容 |
|---|---|---|---|
| 画面 | `frontend` | `npm test` | ドラッグ&ドロップの計算（12件） |
| API | `backend` | `.\gradlew.bat test` | 並び替えなどの計算・API の返事とエラー・起動できるか（26件） |

- API のテストのうち「起動できるか」の1件だけは、DB を起動しておく必要があります（`docker compose up -d`）。ほかのテストは DB の代わりに偽物を使うので、DB は使いません。
- API のテストは、前回から何も変えていないと結果を使い回して実際には動きません。必ず動かしたいときは `.\gradlew.bat test --rerun` にします。

## 使い方
| やりたいこと | 操作 | 機能 |
|---|---|---|
| リストを追加する | 右端の「＋ リストを追加」→ 名前を入れて［追加］ | [1](#func-1) |
| リストの名前を変える | 見出しの「…」→「名前を変更」→ 名前を直して［保存］（Esc でやめる） | [2](#func-2) |
| リストを削除する | 見出しの「…」→「リストを削除」→ 確認で［OK］。中のカードも消える | [3](#func-3) |
| カードを追加する | リストの「＋ カードを追加」→ 追加先リスト・内容・重要度を選んで［追加］ | [4](#func-4) / [9](#func-9) |
| カードを編集する | カードを押す → 内容・重要度を直して［保存］ | [5](#func-5) / [9](#func-9) |
| カードを削除する | カードを押す →［削除］→ 確認で［OK］ | [6](#func-6) |
| カードを並び替える・別のリストへ移す | カードをつかんでドラッグし、落としたい場所で離す（リストの外で離すと元に戻る）。キーボードでもできる（下の「キーボードで操作する」） | [7](#func-7) |
| リストを並び替える | リストの見出しの名前をつかんで、左右にドラッグする。キーボードでもできる | [10](#func-10) |

- **重要度**: カードの左端の色（高：赤、中：黄、低：青）と、右上の「高・中・低」の札で見分けます。
- **キーボードで操作する**: Tab キーでカード（またはリストの見出しの名前）を選び、**スペースキー**でつかむ → **矢印キー**で動かす → もう一度**スペースキー**で置きます。Esc キーでやめると元に戻ります。カードを選んで **Enter キー**を押すと編集画面が開きます。
- **カードの内容**: 1000文字まで入力できます。
- **保存**: どの操作も、すぐにサーバーの DB に保存されます。ブラウザを閉じても消えません（[機能8](#func-8)）。
- **うまくいかないとき**: 画面に赤いお知らせが出たら、API と DB が起動しているか確認してください。ドラッグの保存に失敗したときは、元の位置に戻ります。

**選定理由（指示で決まっていないもの）**
- TypeScript: React と組み合わせるときの標準的な言語。型があるので、Java と同じくミスに早く気づける
- Vite: React の開発環境を作る標準的なツール（Next.js を使わない場合の定番）
- dnd-kit: React 向けのドラッグ&ドロップ用ライブラリ（vuedraggable は Vue.js 用のため不採用）
- Tailwind CSS: HTML（React の部品）に短い名前（例: `p-4` `bg-white`）を並べるだけで見た目を整えられるため、CSS ファイルを別に書く手間が減る。React + Vite と組み合わせて使う例が多い。プロトタイプの style.css はそのまま使わず、見た目を参考にして書き直す
- Spring Data JPA: Spring Boot から PostgreSQL を読み書きする標準的な方法
- npm: React / Vite に最初から付いてくる標準のパッケージ管理ツール
- Gradle: Spring Boot の公式ひな形作成サイト（Spring Initializr）で標準的に選べるビルドツール。設定ファイルが短く読みやすい。「Gradle Wrapper」が付いてくるため、Gradle 本体を別途インストールしなくてよい

### ユースケース
代表的な例を記載しています。

<a id="uc-1"></a>
**1. カードを追加する**
- 主アクター: ユーザー
- 基本フロー:
  1. 「カードを追加」から追加モーダルを開く
  2. 追加先リストを選択する
  3. カードの内容を入力する
  4. 「追加」ボタンを押す
  5. 選択したリストの末尾にカードが追加され、データベースに保存される
- 異常系: 内容が空文字の場合はエラーとなり、追加できない

<a id="uc-2"></a>
**2. カードをドラッグ&ドロップで移動する**
- 主アクター: ユーザー
- 基本フロー:
  1. 移動したいカードをドラッグする
  2. 同じリスト内の別の位置、または別のリストにドロップする
  3. カードの並び順・所属リストが更新され、データベースに即時保存される
- 異常系: リストの外側など、ドロップ不可能な場所に落とした場合は移動前の位置に戻る

<a id="uc-3"></a>
**3. リストを削除する（カード入り）**
- 主アクター: ユーザー
- 基本フロー:
  1. リストヘッダーの「…」メニューから「リストを削除」を選ぶ
  2. 確認ダイアログが表示される
  3. 「OK」を選ぶとリストと中のカードがすべて削除され、データベースに保存される
- 異常系: 確認ダイアログで「キャンセル」を選んだ場合、リストは削除されず何も変わらない

### 非機能要件
- **対応ブラウザ**: 最新版のChrome / Edge / Firefoxを想定
- **レスポンシブ対応**: PCブラウザ専用（スマホ・タブレット対応は対象外）。ドラッグ&ドロップはマウスとキーボードで操作できる（キーボード操作は Issue #53 で追加）
- **想定規模（パフォーマンス目安）**: 小規模利用を想定（リストは数件程度、カードはリストごとに数十件程度）。大量データ向けの性能最適化は行わない
- **データ永続化**: データはサーバー上のPostgreSQLに保存する。ブラウザを閉じたり、ブラウザのデータ（キャッシュ・サイトデータ）を消去したりしても保存内容は残る
- **動作環境の前提**: 利用時はバックエンド（Spring Boot）とデータベース（PostgreSQL）を起動しておく必要がある。当面は自分のPC上（ローカル環境）で動かすことを想定し、インターネット上への公開は対象外とする

### 開発の進め方（GitHub）
変更はすべて「Issue → ブランチ → PR（プルリクエスト）→ マージ」の流れで行う。詳しいルールは [CLAUDE.md](CLAUDE.md) に書いてある。

1. Issue（やることのメモ）を GitHub に登録する
2. Issue 番号の入ったブランチ（例: `feature/2-entities`）を作って作業する
3. PR を作る（本文に `Closes #番号` を書くと、マージ時に Issue が自動で閉じる）
4. ユーザーが GitHub の画面で内容を確認してマージする

main への直接プッシュは、Claude Code の設定（`.claude/`）と GitHub のルールセットの両方で禁止している。

- **Issue と PR の単位**: 1つの工程につき Issue 1つ、PR 1つにする。作業ブランチへのコミットやプッシュは何回してもよく、許可はいらない。ユーザーの許可（マージ）は、工程が終わったときに1回だけ行う。
- **バックエンドの Issue の分け方（予定）**:
  1. ~~読み取り API（エンティティ作成・テストデータ投入・`GET /api/lists`）~~ 完了（Issue #5）
  2. ~~リスト・カードの追加・変更・削除の API（Controller 層・Service 層）~~ 完了（Issue #7）
  3. ~~カードの並び替え・移動の API（`PATCH /api/cards/{id}/move`）と `HelloController` の削除~~ 完了（Issue #9）
  4. ~~画面（React）から API を呼べるようにする設定~~ Vite のプロキシで対応（Issue #13。バックエンドの変更は不要）
- **Claude Code の確認画面**: 作業中に出る「このコマンドを実行してよいですか？」は Claude Code 自体の安全確認で、PR とは関係ない。
